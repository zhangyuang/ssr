# Build Artifacts

This chapter will analyze the build artifacts after executing the `ssr build` command on the default example to help developers better understand the application. The build artifacts of the `ssr` framework are very clear and the quantity is much smaller compared to similar frameworks. The meaning can be seen from the file names.

## Artifact Types

Compared to traditional `SPA` applications that only build pure client-side files, in server-side rendering scenarios, we build artifacts for both server-side and client-side use separately.

```shell
$ tree build
build
├── client # client-side build artifacts folder
│   ├── asset-manifest.json # client-side build artifacts manifest, contains mapping from source files to generated files
│   └── static # static resources
│       ├── css
│       │   ├── Page.9b4ee7a2.chunk.css # common styles
│       │   ├── detail-id.802a30ee.chunk.css # render$id page styles
│       │   └── index.e0ee4d68.chunk.css # index/render page styles
│       └── js
│           ├── Page.bd84ae30.chunk.js # common business js code
│           ├── detail-id-fetch.88ffa1dd.chunk.js # fetch$id file
│           ├── detail-id.7718bdb4.chunk.js # render$id file
│           ├── index-fetch.07aa86b0.chunk.js # fetch file
│           ├── index.b76c09e5.chunk.js # render file
│           ├── runtime~Page.3f285250.js # no need to pay attention, provides some webpack APIs, equivalent to manifest.js generated by old versions of webpack
│           └── vendor.92dcc0b4.chunk.js # third-party modules
└── server # server-side build artifacts folder
    ├── Page.server.js # server-side bundle, built through the framework's underlying server-entry method
    └── static # this folder is not used in non-Vite local development scenarios, no need to pay attention
        └── css
            ├── Page.66b88dee.css
            └── Page.css
```

## Detailed Analysis of Client-Side Artifact Types

Experienced developers will be familiar with what's built in the `client` folder. Client-side build artifacts are generated through [client-entry](https://github.com/zhangyuang/ssr/blob/dev/packages/plugin-vue3/src/entry/client-entry.ts). The only difference is that in server-side rendering scenarios, the framework API we call is `hydrate` hydration mode instead of `render` normal rendering mode.

Developers can use `GENERATE_ANALYSIS=true npm run build` to visually generate client-side build artifacts to determine whether `tree shaking` is effective and whether unused files are introduced.

## Detailed Analysis of Server-Side Artifact Types

Here we specifically mention `Page.server.js` in the server-side build artifacts.

This file is in `commonjs` format and called in the `Node.js` environment. It's built from the [server-entry](https://github.com/zhangyuang/ssr/blob/dev/packages/plugin-vue3/src/entry/server-entry.ts) file in the framework source code. This file only contains business code, namely frontend components. Since the `Node.js` environment cannot directly use `ESM` syntax or recognize `JSX` syntax and style files, we need to do a layer of build processing to ensure that the built artifacts can be successfully executed in the `Node.js` environment.

For server-side file builds, we usually enable the `externals` option, which means externalizing third-party module dependencies. For example:

```js
// Source code
import React from 'react'

// After build
const React = require('react')
```

During build time, the source code of `react` is not packaged together, but modules are dynamically loaded from the `node_modules` folder at runtime. This ensures the size of our server-side build artifacts, containing only pure business code and allowing us to quickly locate problems when errors occur. However, this approach requires the deployment environment to have a `node_modules` folder and contain all modules that will be dynamically loaded in the production environment.

### Common Error Solutions

Since we enabled the `externals` option, this may cause problems in some scenarios. For example, the third-party modules we load have hard-coded dependencies on other modules that are in `ESM` format. For example, some third-party modules will use `lodash-es` instead of `lodash` to run. For such dependencies, we can't externalize and then dynamically load them, which would cause errors. For such module format errors, or modules that depend on style files, we still need to process them by packaging the code together with server-side build artifacts instead of dynamically loading at runtime. Here we can use the [whiteList](./api$config#whiteList) configuration provided by the framework to set modules that need special handling.
